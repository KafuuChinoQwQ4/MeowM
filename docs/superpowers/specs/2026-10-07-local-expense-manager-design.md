# 本地优先个人收支管理系统设计

## 目标

构建一个安卓优先的个人收支管理应用，把支付通知、账单文件和后续可用的数据连接器整理为统一、可追溯的本地账本。第一版的核心闭环是：支付通知采集和账单导入、交易标准化、去重与来源合并、分类修正、余额计算和收支可视化。

第一版不需要用户账号、服务端或云同步。即使离线，用户仍可记账、导入账单、查询余额和查看统计。

## 产品范围

### 第一版包含

- 安卓手机端应用，Rust 领域逻辑和 Rust UI。
- 由用户主动授权的 Android 通知监听，首批支持用户选择的微信、支付宝及银行应用通知。
- 微信和支付宝账单文件导入，导入时提供解析预览、校验、查重和确认。
- 本地统一账户、交易、分类和来源记录。
- 交易去重、跨来源匹配、人工确认和重复导入保护。
- 期初余额及之后的账户余额计算，覆盖银行卡、现金、钱包和信用卡等账户类型。
- 收入、支出、转账和退款处理；转账不计入收入或支出，退款关联原交易并抵减净支出。
- 用户可编辑分类、手动修正及基于商户/关键词的自动分类规则。
- 月度收入/支出趋势、分类占比、账户余额变化和商户排行。
- 每账户原币种及人民币报表金额；来源账单提供汇率时使用来源值，缺失时由用户输入。
- 手动加密备份与恢复；用户可在设置中选择是否启用应用锁。

### 后续评估

- PayPal、银行等正式授权 API 或其他合规数据连接器。
- 在线汇率、云备份、多设备同步、预算和周期性交易。
- 模型辅助分类。第一版分类规则需可解释，不能在后台静默改写已确认账目。

## 采集与导入流程

### Android 通知

使用 Android `NotificationListenerService` 获取系统分发的新通知。用户必须自行在系统设置中授予通知访问权限，并能在应用设置中启用或停用每个来源。通知监听只处理系统通知，不使用无障碍服务读取微信、支付宝或银行应用内部页面。

Android 平台适配层提取来源包名、可用标题和正文、通知标识及发生时间，并将必要字段传给 Rust 核心。Rust 解析适配器根据来源应用和通知格式提取金额、方向、商户、账户线索和置信信息。明确但尚未验证的结果建立待确认交易；字段缺失或解析不确定的结果留在待处理列表。通知正文默认不长期保存，也不写入日志。

通知访问可能被用户关闭、系统或设备厂商限制，通知内容也可能缺失或被隐藏。因此通知采集是快捷输入，不作为账目完整性的保证。应用应显示监听授权和来源状态，但不得声称每笔支付都必然捕获。

### 账单文件

用户选择微信或支付宝账单文件后，应用在本地解析并展示导入预览。预览列出识别到的记录数、无法解析的行、时间范围、币种以及疑似重复项。用户确认后再写入账本。导入文件只在处理过程中使用，完成后默认不长期保留；用户可主动选择保留来源文件。

解析器应版本化，并保留足够的来源字段用于追溯和将来重新解析。文件格式变化或行校验失败时，导入应报告具体问题，避免部分失败后形成不清楚的账目状态。

### 匹配和去重

一条标准交易可以关联多条来源证据，例如同一消费的支付通知、微信账单行和银行卡账单行。去重按以下顺序进行：

1. 同一来源提供稳定交易号时，使用来源标识与交易号组成幂等键。
2. 没有稳定交易号时，按金额、币种、时间、商户、账户和来源类型生成候选匹配。
3. 唯一且足够可靠的候选可自动合并；有多个可能项或证据冲突时要求用户确认。
4. 用户确认的合并或拆分结果需要保留，重新导入时不得再次创建重复交易。

通知和账单中的交易时间可能有时区或精度差异。匹配评分应容忍有限时间差，但不能单凭金额和日期自动合并。

## 统一账本数据概念

- **账户**：用户持有或欠付资金的地方，包含账户类型、名称、币种、期初余额和基准日期。类型至少包括现金、银行账户、电子钱包、PayPal 和信用卡，且允许用户新增账户。
- **渠道**：产生或承载交易的服务，例如微信支付、支付宝、银行应用或现金。渠道和资金账户是不同维度。
- **交易**：标准化账目，包含方向/类型、原币金额、人民币报表金额、时间、商户/对方、账户、渠道、分类、备注和状态。
- **来源证据**：通知事件或导入账单行，包含来源标识、外部交易号（若有）、导入批次和原始字段摘要；可关联到一笔交易，支持审计及跨来源补全。
- **关系**：用于表示退款对应的原支出，以及转账的转出与转入账户记录。
- **分类规则**：用户定义的商户或关键词匹配规则，记录目标分类和优先级。

所有金额使用定点十进制或最小货币单位整数保存，不使用二进制浮点数。原币金额与报表金额同时保留，汇率及其来源也需记录，便于复核历史统计。

## 余额和交易语义

每个账户使用期初余额及基准日期作为计算起点，只累加基准日期之后的已确认账目。用户可以选择导入更早交易并调整基准日期。待确认通知不改变正式余额或统计。

账户间转账同时影响转出和转入账户，但不改变总收入/支出。信用卡消费增加应付余额并计入消费；偿还信用卡是资金账户与信用卡账户间的转账。退款与原交易关联，保留退款记录并在净支出中抵减，不删除原消费。账户余额差异可通过有原因、有时间的调整记录修正。

## 分类和可视化

系统提供可编辑的默认分类。用户能手动更改分类，并可把修改保存为后续交易的规则。自动分类结果应能显示匹配规则或推荐原因；未能可靠分类时使用待分类状态。

图表只纳入已确认交易。第一版展示月度收入/支出趋势、支出分类占比、账户余额变化和商户排行。退款单独显示，并在净支出统计中抵减。多币种总览按交易保存的人民币报表金额计算；账户详情仍显示账户原币余额。

## 技术架构

- **Rust 核心**：统一领域模型、本地数据库访问、交易与余额规则、账单解析器、通知解析器、去重匹配、分类规则和统计查询。平台无关部分尽可能保持纯 Rust，以便后续复用。
- **Slint UI**：安卓优先的 Rust 界面。交互通过明确的应用服务接口调用 Rust 核心。
- **Android 适配层**：少量 Kotlin/Java 代码实现 `NotificationListenerService`、通知访问设置跳转、Android 生命周期和必要的安全存储/文件选择系统集成；只通过窄接口传递事件，不承载账本业务规则。
- **本地存储**：应用私有目录中的 SQLite 数据库；无远端服务依赖。数据迁移采用显式 schema 版本。
- **备份**：导出自包含、加密的备份包，包含交易、账户、分类、规则、关联证据和数据库版本。恢复前校验密码与文件完整性，并预览覆盖/合并策略。备份密码不与备份文件一同保存。

应用锁为用户可选设置，可使用设备支持的生物识别或系统凭证进行本地验证。关闭应用锁不应影响账本数据；用户可随时更改该设置。

## 失败处理和隐私要求

- 无法解析的通知显示为可忽略或手动补录的待处理项，不阻断后续通知处理。
- 账单导入先验证再提交；失败批次不应留下半导入数据，并允许用户移除整批导入。
- 数据库写入、文件读取或备份恢复失败时给出可理解的错误和重试路径，不丢弃未确认数据。
- 通知内容、账单原始行、账户名称和交易备注不得进入普通日志或崩溃报告。
- 网络不是第一版运行条件；若将来引入连接器，必须单独设计授权、凭证保存和撤销流程。
- 系统通知权限必须由用户主动开启；应用提供来源开关、权限状态、数据删除和完整导出能力。

## 验收要点

1. 关闭网络时，用户仍可添加账户、导入账单、确认交易、查看余额和图表。
2. 同一个账单重复导入不会创建重复交易；银行账单行可与已有微信/支付宝交易匹配。
3. 支付通知产生待确认项，确认后影响余额；与后续账单匹配时更新同一交易并保留两种来源。
4. 转账不影响收支合计；信用卡还款不重复计入消费；退款能关联原消费。
5. 基准日期前的导入不会静默改变余额；人民币及外币金额和汇率信息可追溯。
6. 备份可加密导出并在干净安装中恢复；错误密码或损坏备份不得部分覆盖现有账本。
7. 用户能关闭某个通知来源或应用锁，并能删除单笔交易、导入批次及全部本地数据。

## 明确限制

通知内容和 Android/厂商后台策略不受本应用控制，不能保证完整捕获。个人微信、支付宝、PayPal 和银行账户是否提供可用于个人授权读取的正式接口，需要逐个平台评估；第一版以本地通知与文件导入为准。第一版不实现云同步、服务端账户体系、实时汇率或模型自动改账。
